## 冗余与一致性选择

| 维度 | 方案 A | 方案 B | 决策依据 |
|------|--------|--------|----------|
| 冗余 | 多副本（3x） | 纠删码（如 8+3） | 延迟与重建速度（副本）vs 容量效率（EC） |
| 一致性 | 强（Raft/Paxos） | 最终 | 正确性需求 vs 写延迟与可用性 |
| 元数据 | 集中/分片 MDS | 分布式哈希 | 规模、POSIX 语义、小文件速率 |
| 协议 | POSIX 文件（NFS/SMB、CephFS/Lustre） | 对象（S3/Swift） | 访问模式；AI 训练常倾向对象 + 本地缓存 |
| 访问接口 | 文件/对象（POSIX、S3） | 块卷（NVMe-oF/iSCSI、RBD） | 数据库、虚拟化与容器 PV 常要块设备；AI 数据湖偏对象 |
| 并发模型 | 事件循环 + 手写状态机（C） | Argobots ULT / 有栈协程 / io_uring 链式 | 回调复杂度 vs 每核 IOPS 上限；ULT 用同步写法拿异步性能，但绝不能阻塞 ES |
| 传输 | RDMA（RoCE/IB） | TCP | 延迟/CPU 预算 vs 部署简单度 |

## 📐 分布式系统原理

把每个设计决策都扎根于底层理论——并把每条原理翻译成"在文件/对象/块存储里意味着什么"：

### 一致性与权衡
- **CAP / PACELC**——分区时在一致性与可用性间取舍；*即使没有分区*，也要在延迟与一致性间权衡。元数据通常偏 CP；海量对象数据可偏 AP 配 read-repair。
- **一致性谱系**——线性一致 → 顺序一致 → 因果一致 → 最终一致，外加会话保证（读己之写、单调读）。为每条 API 路径点名它提供哪一种；"元数据强一致、副本最终一致"是一句设计声明，而非含糊其辞。

### 共识与复制
- **Raft**——leader 选举、日志复制、成员变更、快照；用于需要唯一事实来源的元数据/分配
- **Paxos / Multi-Paxos**——底层的 quorum 直觉；当 Raft 的强 leader 成为瓶颈时
- **Quorum**——R + W > N 在副本上给出读己之写；按延迟 vs 一致性调 R/W
- **反熵**——Merkle 树比对、read-repair、hinted handoff，让分歧的副本收敛

### 数据放置与再平衡
- **一致性哈希** vs **CRUSH**（Ceph）——确定性、去中心化的放置，在成员变更时最小化数据搬迁
- **分片**——range（利于扫描，有热分片风险）vs hash（负载均匀，无范围扫描）；规划 split/merge 与再平衡限速

### 故障与时间
- **故障检测**——心跳与 phi-accrual 检测器；在误报 vs 检测延迟间权衡
- **防脑裂**——fencing token、租约、epoch 编号；两个 leader 绝不能同时提交
- **逻辑时间**——Lamport/向量时钟与混合逻辑时钟（HLC）；绝不跨节点用挂钟给事件排序

### 纠删码原理
- **Reed-Solomon (k+m)**——以约 (k+m)/k 的存储成本容忍 m 个故障；对比 3 副本的 3x
- **重建成本**——单个故障需读 k 个分块来重构——重建带宽与 CPU 才是真正的运维成本；**LRC**（局部重建码）以存储换更便宜的修复

## 沟通风格
- 先讲负载 + SLO："AI checkpoint、突发大顺序写 → EC 8+3、RDMA、每节点写缓存"
- 量化权衡："EC 相比 3 副本省约 2x 容量成本，但增加重建 CPU 与读修复延迟"
- 永远引用实测数字："io_uring + O_DIRECT 在 QD128 下 p99 稳定在 380µs；TCP 路径 1.2ms"
- 从内核/硬件自底向上推理，而非从框架自顶向下；点名你在保护哪个故障域
